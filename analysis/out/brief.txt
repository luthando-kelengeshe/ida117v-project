1. PROJECT PURPOSE 
In a team of no more than six, identify a real service-delivery problem in South Africa and develop an end-
to-end, reproducible machine -learning solution. The project must move beyond model accuracy: it must 
establish a credible problem, use lawful and relevant data, compare robust baselines with neural models, 
control overfitting, optimise one justified champion, test which components matter, and determine whether 
the observed improvement is statistically credible. 
Learning outcomes 
• Frame a public-service problem as a measurable data -science task with clear stakeholders and success 
criteria. 
• Acquire, audit, visualise and prepare real data without leakage. 
• Build reproducible traditional and neural-learning pipelines and evaluate them fairly. 
• Diagnose overfitting, optimise a selected model, conduct an ablation study and apply a paired 
statistical test. 
• Deploy the selected model through a usable user interface that supports stakeholder -facing prediction 
and responsible interpretation. 
• Communicate limitations, ethical risks and actionable recommendations for a South African context. 
2. PROJECT SCOPE AND DATA 
Select a classification problem connected to service delivery. A regression or forecasting problem requires 
prior lecturer approval and a statistically appropriate paired alternative to McNemar’s test. The outcome 
must be meaningful to a public-service stakeholder—not merely convenient to predict.

3. ASSESSMENT QUESTIONS 
Answer every question in the submitted technical report. Marks in brackets indicate the relative depth 
expected. 
QUESTION 1          Total Marks [10] 
1.1 Define the South African service -delivery problem, affected population, decision -maker and intended 
benefit. Convert it into a classification task by specifying the unit of prediction, inputs, target classes 
and prediction horizon.           (4) 
1.2 State one primary technical metric and at least one service -delivery success indicator. Explain the cost 
of false positives and false negatives.         (2) 
1.3 Justify the dataset’s relevance, provenance, licence, coverage and limitations. Identify POPIA, privacy, 
fairness and misuse risks and propose safeguards.       (4) 
QUESTION 2          Total Marks [18] 
2.1 Create a data dictionary and audit class balance, duplicates, missingness, invalid values, outliers and 
possible leakage.            (4) 
2.2 Present at least five purposeful visualisations: target distribution; missingness/data quality; two 
feature–target relationships; and one geographic, temporal or subgroup view. Each figure must have a 
title, units, readable labels and an interpretation.        (6) 
2.3 Split data before learning transformations. Justify train/validation/test or nested cross -validation 
design, including stratification/group/time constraints. Reserve the test set for final evaluation only. 
 (3) 
2.4 Implement cleaning, encoding, scaling, imputation, feature engineering and imbalance treatment inside 
a reproducible pipeline. Explain choices and prevent leakage.      (5) 
QUESTION 3          Total Marks [18] 
3.1 Build a transparent naïve baseline (for example, majority/stratified DummyClassifier) and explain 
what it establishes.           (2) 
3.2 Train at least four substantive models on identical data splits: at least two traditional models and at 
least two neural-learning models. The naïve baseline does not count among the four.   (10) 
3.3 Traditional examples include Logistic Regression, Decision Tree/Random Forest, Support Vector 
Machine, Naïve Bayes or gradient boosting. Neural requirements include an MLP and one task -
appropriate second architecture (for example, CNN for imagery, GRU/LSTM for sequences, or an 
approved tabular neural network).         (3)

3.4 Document architecture/hyperparameters, loss, optimiser, epochs, batch size, regularisation, early 
stopping, seeds, compute environment and reproducible training procedure.    (5) 
3.5 Provide a concise rationale linking each model family to the data and problem.   (2) 
QUESTION 4          Total Marks [16] 
4.1 For every substantive model, report the same held -out metrics. Include accuracy and macro -F1; add 
precision, recall, weighted -F1 and ROC -AUC as appropriate. For imbalance, include PR -AUC or 
justify its omission.           (4) 
4.2 Provide a classification report and confusion matrix for every model; provide ROC curves on one 
common figure (one-vs-rest macro/micro curves for multiclass).     (5) 
4.3 Compare all models with a clear table and bar chart. Show cross -validation means and variability or 
confidence intervals where feasible. Select the provisional champion using validation —not test —
performance.           (3) 
4.4 Test for overfitting using train -versus-validation performance and learning curves; for neural models 
also show training/validation loss and metric curves. Diagnose gaps and discuss early stopping, 
dropout, weight decay, pruning or other controls used.       (4) 
QUESTION 5          Total Marks [10] 
5.1 Optimize only the strongest validation model using a documented method such as grid search, random 
search, Bayesian optimisation or Optuna. Define the search space and scoring rule.   (4) 
5.2 Use cross-validation or a strict validation set; do not tune on the held -out test set. Compare pre - and 
post-optimisation results and report the chosen hyperparameters.    (4) 
5.3 Evaluate the final locked pipeline once on the test set and explain whether the improvement is 
practically meaningful.           (2) 
QUESTION 6          Total Marks [10] 
6.1 Conduct at least three controlled ablations. Remove or alter one feature group, preprocessing step, 
imbalance method, regulariser or architecture component at a time while keeping split, seed and 
evaluation protocol fixed. Report on the change in performance and interpret what the system depends 
on.             (5) 
6.2 Compare the optimized champion with the strongest comparator on the same  held-out cases using 
McNemar’s test. Show the 2 × 2 correctness table, state H₀/H₁ and α = 0.05, report the statistic/exact p-
value, and distinguish statistical from practical significance. Use the exact binomial version when 
discordant counts are small.          (5)

QUESTION 7          Total Marks [10] 
7.1 Deploy the final optimized model through a working user interface. The interface may be developed 
with Gradio, Streamlit, Flask, FastAPI with a web front end, or another lecturer -approved framework. 
A notebook cell alone is not a user interface.        (2) 
7.2 Allow a user to enter or upload valid input, run the complete saved preprocessing -and-model pipeline,

7.4 Provide deployment instructions and either a stable demonstration link or a locally reproducible launch

8.1 Translate findings into a realistic recommendation for the stakeholder. State limitations, uncertainty,

8.2 Submit a reproducible repository/package with README, environment/requirements, fixed seeds,

redistribute data if its licence forbids it.         (3) 
8.3 Deliver a concise team presentation and live or recorded interface demonstration. Defend the 
modelling choices and include a signed contribution statement; individual marks may be moderated 
where evidence of contribution differs.         (2)

4. REQUIRED EVIDENCE AND EXPERIMENTAL RULES 
Requirement Minimum acceptable evidence 
Data split integrity 
A diagram or written sequence showing split -before-fit; preprocessing 
learned on training folds only; shared held -out cases for every final 
comparison. 
Model set 
Naïve baseline + ≥4 substantive models: ≥2 traditional and ≥2 neural. 
Hyperparameters and random seeds disclosed. 
Core visual evidence 
EDA figures, model comparison chart, confusion matrices, ROC curves, 
learning curves, neural loss/metric curves and ablation plot/table. 
User-interface deployment 
Working interface loads the saved final pipeline, accepts valid input, returns 
a prediction and confidence where appropriate, handles invalid input, 
communicates limitations, and can be launched from documented 
instructions. 
Classification evidence 
Per-model classification reports with class labels and support; class -sensitive 
interpretation rather than accuracy alone. 
Optimisation 
Search strategy, ranges, validation score, selected configuration and locked 
final test result. 
Ablation 
≥3 one -change-at-a-time experiments, same evaluation protocol, 
performance deltas and interpretation. 
McNemar validation 
Paired predictions on identical test cases; table counts: both correct, 
champion only correct, comparator only correct, both wrong; hypotheses, α, 
p-value and conclusion. 
Overfitting 
Quantified train –validation gap plus learning curves; mitigation and 
limitations discussed.
